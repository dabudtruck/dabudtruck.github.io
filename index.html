Scoped, Revocable, Auditable

Giving an AI coding agent real access to a production-style infrastructure fleet — and the two times my own controls broke, and what that actually taught me.

The problem

I run a small self-hosted infrastructure fleet — a cloud server, a home-automation controller, a set of NixOS-based edge devices — and I use an AI coding agent as a hands-on collaborator for running it: reading logs, calling internal APIs, deploying config changes, working live on real boxes rather than guessing from documentation.

That's genuinely useful. It's also an access-control problem the moment it stops being hypothetical. An agent that can usefully act on your infrastructure is, by definition, one that can do damage — by accident, or if its own credentials ever leak. "Just hand it my key" is the fast path, and the wrong one. The real engineering question isn't whether an agent should touch production-shaped systems. It's what safe delegation actually requires.

The design

Four principles, each backed by a concrete mechanism rather than a policy statement:

  1. 01

    Least privilege, scoped at the source

    Credentials live in a vault isolated from my own — accessible only through a read-only, non-interactive identity. That identity can read what's been provisioned; it cannot create, edit, or delete a single item, even by accident. Every credential-bearing item still requires my own human login to originate.

  2. 02

    Time-boxed by default, not by policy

    Access expires on a short, forced clock rather than relying on anyone remembering to revoke it. A forgotten credential decays on its own instead of sitting valid indefinitely.

  3. 03

    Every action, a named event

    Each credentialed call requires a mandatory, human-readable reason string, logged. Nothing the agent does with real access happens silently.

  4. 04

    A control plane the agent cannot reach

    Granting, renewing, and revoking access are commands I run myself, outside the agent's own execution context. It can check status. It cannot touch the switch.

How it's built

The vault itself is Proton Pass — a dedicated vault, separate from my personal one, so a problem here can't touch anything else. The mechanics behind the four principles above:

A scoped agent identity, not a login
Proton Pass's CLI has an agent subsystem, distinct from a normal user session: read-only, bound to one vault, with a forced one-month expiration and a mandatory reason string on every read, logged.
An isolated session, kept separate on purpose
The agent's login session lives in its own directory, never the one my own CLI session uses. This isn't theoretical caution — early in setup, a shared session briefly gave the agent read access to every vault I own, before the two were split apart. Keeping them separate is what actually prevents that.
A dedicated SSH agent, one key only
A second SSH agent process holds just the one key scoped for this purpose — independent of my own system SSH agent, and independently revocable without touching my own SSH access at all.
One wrapper script per capability
Never general-purpose credential access. Each script authenticates, injects the secret only into that single child process's environment — masked by default, so even an accidental echo prints a placeholder instead of the real value — and never assigns a secret to a shell variable, so it can't leak into shell history or process listings.
Representative shape of one wrapper script
ha_api() {
  local reason="$1"; shift
  # every call carries its own audit reason
  PROTON_PASS_AGENT_REASON="$reason" \
    pass-cli run --env-file <(pass-cli item env home-assistant-token) -- \
    curl -sf -H "Authorization: Bearer $HA_TOKEN" "$@"
}

# usage:
ha_api "checking thermostat state for a bug report" -- /api/states

The reason string matters more than it looks — it's the mechanism behind the fix to the incident below: not a promise to be more careful, but making the narrow, audited path (one named field at a time) the only path a wrapper script can take.

Where it actually broke

Two real incidents mattered more than the design on paper.

Incident 2026-08-18

A lapsed credential doesn't just go stale — the record disappears

I assumed an unrenewed token would simply need reactivating. It didn't: past its expiration window, the agent identity itself was removed outright, and the normal renew command failed with "not found." Recovery meant fully recreating the scoped identity from my own login, not renewing it.

The real lesson wasn't the mechanic — it was that a longer default expiration is a mitigation, not a fix. The actual fix is a recurring human reminder to renew, because any fixed window eventually lapses the same way if nothing prompts action before it does. I try to design controls that degrade safely, not ones that quietly assume a human will remember.

Incident 2026-08-27

A boundary I designed got bypassed by an honest debugging shortcut

Mid-troubleshoot on a broken integration, the rule "never dump a full credential item — request one named field" got violated. A hand-rolled redaction script tried to denylist known secret-bearing field names, missed one type it hadn't anticipated, and that value reached the agent's own output unredacted.

Denylisting is exactly the failure mode the original rule existed to prevent, and it failed the same way anyway, under time pressure, written by me. The fix wasn't "be more careful" — it was retiring the entire shortcut: request fields one at a time by name, and if a full inspection is ever unavoidable, redact by an allowlist of known-safe fields, never by enumerating every possible secret field across item types.

I'd rather show a system where I found and fixed a real gap than one that's never been tested.

Why this generalizes

None of this is specific to a home server. It's the same shape as any real "give an autonomous system delegated access to production" problem: scope tightly, expire by default, audit everything, keep a human-only kill switch outside the agent's reach — and go back and look for where your own controls got quietly worked around under real pressure, because that's where the next incident actually comes from.
